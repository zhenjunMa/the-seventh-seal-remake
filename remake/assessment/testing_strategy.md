# 第七封印重制测试体系设计方案

日期：2026-10-29。适用于从原版安装文件提取内容、使用 Phaser 重制游戏的后续开发。

以共享机制测试保护游戏规则，以内容校验保护持续增加的地图和剧情，以少量真实浏览器流程保护 Phaser 集成。普通任务按影响范围验收，区域阶段验收覆盖新增事件链，版本验收覆盖已实现游戏范围。新增内容主要增加数据和阶段案例，日常执行时间由受影响范围决定。

第一版已实现 task、phase、release、audit 档位、递归代码依赖选择、便携结果复用、区域遍历分离及真实 Phaser 生命周期检查页。动态数据变化和缓存失效仍采用保守的便携全范围；分地图语义摘要、完整跨区域依赖图、数据驱动阶段案例及浏览器自动调度仍是目标设计。已实现命令见 [工具说明](../runtime/tools/README.md#测试职责与运行)，当前任务和完成状态仍只在 [开发计划](validation_design.md) 维护。

## 项目边界与质量目标

正式生产链是原版只读输入、解析与导出、运行内容包、游戏规则、Phaser 场景和浏览器。测试需要分别回答三个问题：内容是否正确还原、规则是否正确执行、玩家是否能正常游玩。

当前实现有几个决定测试方式的事实：

- Phaser 固定为 3.90.0，正式入口显式使用 Canvas 渲染。输入和音频由既有控制器管理，Phaser 内建输入和音频关闭；移动碰撞使用 `MovementMap`。依据见 [PhaserRuntime](../runtime/web/phaser/runtime.mjs)。
- `WorldStore` 保存世界；`SceneController` 准备和提交地图；`BattleController` 管理战斗并提交结果。Phaser Sprite 和场景显示对象不持有另一份可保存进度。依据见 [架构说明](../runtime/architecture.md)。
- 已有 `ActionClock`、20ms 战斗逻辑步、可注入资源加载器和共享剧情执行器，可用于快速、确定性的行为验证。
- 素材、原程序及部分历史证据不随代码仓库提供。代码环境与素材环境承担不同验证职责，缺少材料不能被记作完整通过。

原版数值、事件条件、奖励、资源身份和来源字节按已恢复合同核对；现代化移动手感、缩放和资源策略按项目明确采用的行为验收。来源保真不能把旧渲染实现或曾经的临时代码固化为唯一正确答案。

## 按验证对象分层

Node 和 Python 是执行工具，不是测试层级。现有 runtime、content、source 等组可以保留兼容入口，新增分类同时记录层级、系统、内容范围和环境。

| 层级 | 主要验证对象 | 使用的环境和输入 | 增长方式 |
| --- | --- | --- | --- |
| 规则单测 | 数值、资格、状态转换、RNG、移动几何、奖励去重、配置合并 | Node 或 Python；最小固定输入，无浏览器、原安装或真实媒体依赖 | 新机制和高风险规则边界增加案例 |
| 系统组件测试 | 剧情事务、地图准备、战斗结算、存读档、资源租约、取消与迟到回调 | 正式控制器与规则，受控时钟及加载器；小型有效内容包 | 新系统边界或机制交互增加案例 |
| 内容校验 | 地图、NPC、出口、条件、程序、技能和资产引用的完整性及能力准入 | 真实登记和生成内容；尽量只读取结构化数据 | 新内容增加数据，复用统一校验器 |
| Phaser 集成测试 | 实际场景状态、显示适配、纹理与对象生命周期、缩放和输入连接 | 浏览器中的固定 Phaser 版本；少量合成资源或真实小资源集 | 新引擎连接或表现机制增加案例 |
| 游戏流程验收 | 进入、事件、战斗、离开、保存恢复，以及画面、声音和操作体验 | 正式 `/` 入口、实际渲染和正式资源、隔离存档 | 新阶段增加有边界的事件链；固定核心冒烟保持精简 |
| 来源与构建验证 | DAT、TLK、ANM、CHR、DGP 等解析，导出像素、图集及增量构建 | 对应原版输入、独立核对值、实际 CLI、媒体工具 | 新格式、解析器或导出策略增加案例；旧输入复用有效结果 |

单测验证规则，回归表示重新执行用于发现退步的验证项；回归可以包含表中的任何一层。不要再把所有 Node 测试都称为单测，也不要把浏览器实玩通过当成下层规则已完整验证。

## 共享机制和区域内容的分工

### 新增内容复用已验证机制

新增同机制地图、NPC、宝箱、商店或技能，优先添加登记、来源和案例数据。统一校验器对新增或受影响内容检查身份、引用、条件、能力和资源闭包；区域案例描述实际前置、玩家操作和可观察结果。

不为每个对象再复制一份完整测试程序。内容案例通过相同运行器执行，保持原地图、入口和物品身份，能够发现登记接错、条件写错及奖励配错。

| 内容变化 | 应增加的验证 | 可复用的机制保障 |
| --- | --- | --- |
| 新增使用现有处理器的普通宝箱 | 原箱子身份、钥匙、奖励、标志和资源引用；所属事件链的取得与恢复结果 | 缺钥匙、背包满、动画失败回滚、重复开箱、保存重载的通用规则 |
| 新增现有伤害类型的怪物技能 | 原技能索引、参数、目标、动作接触和媒体绑定；必要的真实绑定样例 | 命中、扣费、伤害、死亡、反击和结算的共享规则 |
| 新增任务事件链 | 实际入口、条件转换、奖励和跨区依赖；该链关键成功、拒绝及恢复分支 | StoryFlow 控制流、事务提交、取消和迟到回调规则 |
| 新增控制流指令、复活机制或资源策略 | 对应规则与组件案例，必要的来源差分，以及一个正式集成场景 | 已有其他指令、角色和地区的无关组合 |
| 调整对白、面板位置或字号 | 受影响内容引用、字体字符和浏览器表现 | 未变化的战斗与导出规则 |

通用机制可用小输入，但需要保留少量真实来源的绑定案例，保证测试机制和正式内容确实接通。

### 静态完整性和动态覆盖分别控制成本

所有开放入口的引用和能力准入都必须完整校验，包括当前旗标不成立时仍可达的分支。增量校验只能复用输入未变的已验证结果；不能以当前开发存档走不到为由跳过未知操作码、缺失依赖或未实现处理器。

昂贵的动态执行按范围进行：普通任务执行受影响入口，区域收口执行该阶段约定的完整事件链和相关分支，扩大共享机制影响时执行对应机制在其他内容中的代表实例。全量遍历已接入 NPC 的三态或多态组合归扩大检查，避免每个内容任务都重新执行旧地区的全部交互。

代表实例按行为差异选择，例如直接发奖、条件发奖、嵌套演出、跨图提交和战斗返回；不能仅按地图名随机抽取。对使用新机制的每个正式绑定仍做结构校验，发现例外时新增独立类别或真实回归案例。

组合覆盖围绕已知交互风险设计。通用事务层覆盖每种副作用在失败或取消后的回滚；每条新事件链再核对实际接线和关键中断点，无须对每个 NPC 重复整套等价故障注入。主线前置、关键条件边界、消耗和奖励原子性不能用随机抽样代替。

### 区域案例的最小结构

后续每条新阶段事件链使用同一份案例数据描述，不另建区域专用测试执行器：

| 字段 | 应记录的内容 |
| --- | --- |
| 稳定身份与范围 | 区域、剧情阶段、正式入口，以及使用的机制 |
| 初始状态 | 可追溯的起始存档或最小世界、必要旗标、队伍与物品；注明自然前置或开发交接 |
| 操作与节点 | 正式交互、选择、战斗结果、出口，以及需要保存恢复或注入失败的关键节点 |
| 预期结果 | 具体旗标、物品与金钱差额、队伍、地点、NPC 布置和事件完成状态 |
| 重进与异常 | 重复交互不重复提交，关键拒绝、失败或中断后的世界与可重试状态 |

案例运行器验证状态迁移，浏览器流程验证实际接线与体验。长主线新增关键中途恢复节点，防止只测入口和结尾而遗漏软锁；普通无副作用对白无需复制全部存档和故障矩阵。预期结果应来自已确认的来源语义或明确的重制设计，不能直接把当前程序执行结果录成答案。

## Phaser 集成的重点

### 场景生命周期和异步所有权

固定验证探索、剧情、菜单、战斗与返回之间的阶段切换，区分 pause、sleep、shutdown 和 destroy。Phaser 的 sleep 会保留对象，外部事件和回调仍可能作用于休眠场景；这要求项目明确取消信号、会话代次和监听器归属。[Phaser 3.90 场景实现](https://raw.githubusercontent.com/phaserjs/phaser/v3.90.0/src/scene/Systems.js)

核心断言是暂停期间不推进游戏、恢复后不补算后台停留时间、旧场景迟到回调不改变新世界、重新进入不叠加监听器和重复提交。组件层用延迟完成的假加载器验证竞态，真实 Phaser 场景再验证事件连接和重进结果。

### 逻辑时间与渲染帧分开验证

规则与组件测试主动推进项目时钟，不等待真实动画时间。围绕 20ms 逻辑步检查阈值前后、一次跨越多步和剩余时间；使用固定 RNG 检查行动、命中与奖励。

对移动和调度选取等时长的不同 delta 分割，验证在项目约定的 30、60、120Hz 输入下具有相同的逻辑结果或明确允许的误差。暂停恢复首帧的丢弃策略单独验证，不把它和普通运行混在同一等时长比较中。

真实浏览器验证继续使用正式循环，关注画面与逻辑同步。跳过渲染、直接推进规则得到的通过记录，只能归为规则或组件结果。

### 纹理和显示对象的生命周期

Phaser 的纹理由 Game 级 TextureManager 管理，多个显示对象可能共享纹理。场景切换不能假定所有共享资源自动释放。[Phaser 3.90 TextureManager](https://raw.githubusercontent.com/phaserjs/phaser/v3.90.0/src/textures/TextureManager.js)

围绕现有 `TextureCache`、`BattleResources` 和 `BattleSurface` 验证：仍被使用的图集不会提前移除；离场释放本次租约；取消准备不会安装过期资源；重复进入后纹理、监听器和对象池数量在预热后趋于稳定。

测试应考虑常驻资源和有界对象池，不能要求每次离场后全局纹理数为零。解码位图估算大小、Canvas 占用和纹理数量是可观测指标，不等于实际 GPU 内存。

### 真实渲染和浏览器连接

当前 Canvas 是必须验收的渲染路径。像素缩放、图层深度、裁切、加色、阴影、字体与焦点使用少量专门场景验证；实际音频和输入走项目当前控制器。项目未使用的 Phaser 物理、键盘和音频插件不进入默认测试矩阵。

以后正式引入 WebGL 时，再把 Canvas 与 WebGL 的差异、混合方式和纹理上传列为迁移专项。不要因为引擎具备该功能，就现在对每个地图增加两套渲染回归。

Phaser.HEADLESS 不创建渲染器，而且仍依赖 DOM。它可用于部分引擎逻辑验证，不能替代渲染检查，也不是直接在纯 Node 中运行完整 Phaser 的捷径。[Phaser 3.90 常量说明](https://raw.githubusercontent.com/phaserjs/phaser/v3.90.0/src/const.js)

浏览器自动化可集中使用一个工具，建议后续采用 Playwright；Node 的假 Canvas 只用于协议和行为断言。无界面运行的浏览器与 Phaser.HEADLESS 是两种模式，前者仍可执行实际 Canvas 渲染。等待应使用可观察状态和有界超时，避免固定 sleep。[Playwright 断言文档](https://playwright.dev/docs/test-assertions)

### 视觉与性能检查

固定逻辑分辨率、缩放、渲染器、资源、浏览器环境和采样时刻，选择少量关键画面。来源解码的图块可以精确比较像素；浏览器动态画面按稳定区域、容差和人工观感判断，不把跨设备全屏逐像素一致作为默认门槛。

性能检查单独记录冷启动、首次进入、热切换、首个技能、连续战斗与离场释放。常规浏览器冒烟只发现明显卡死、资源异常增长和请求失败；精细耗时比较在固定环境执行，不用共享机器上的单次毫秒差异阻断普通任务。

角色操作手感、战斗节奏、对白可读性、音效衔接和主线引导保留人工体验验收。自动化负责稳定复现和发现机械错误，截图一致或事件执行完成不能独立证明游戏体验合格。手动验收聚焦本次改变的体验，版本收口再检查连续游玩与长流程。

## 原版安装文件与可重建运行包

原版版本先建立文件身份清单。每种解析格式分别保留最小合法、关键变体、截断和非法输入案例；新增原文件走既有解析器时，增加内容核对，出现新变体或新语义时才扩展格式测试。

来源差分按原输入、解析器和转换规则的身份复用。新区域核对新增来源及其生成产物；解析器改变则核对该解析器处理的全部受影响输入。媒体打包改变时检查可见像素、alpha、帧坐标和引用结果，不要求优化前后图集文件布局及字节完全相同。

版本验收必须保留一条“干净检出加声明的原版安装文件，生成可运行内容包，再从正式入口启动”的生产链验证。它用于发现开发机隐藏缓存、旧 evidence 和未声明工具依赖；普通任务执行相应增量构建和资源检查。当前首次构建尚未打通的限制仍以项目说明和开发计划为准，测试体系改造不能将其自动标记为解决。

发布范围的输出清单、资源存在性和文件身份需要完整核对；昂贵的重复解码可复用严格匹配的有效结果。平台检查覆盖项目实际承诺的平台与浏览器，尤其注意路径大小写、媒体解码、字体和保存接口，不把所有浏览器与所有内容相乘作为普通任务门槛。

## 每类任务执行什么

### 验收档位

| 档位 | 适用时机 | 必须覆盖的范围 |
| --- | --- | --- |
| task | 普通功能或修复任务 | 受影响规则、组件、内容闭包；代码涉及的固定核心冒烟；页面变化补受影响浏览器场景 |
| phase | 一个区域剧情阶段或共享功能收口 | task 加该阶段完整事件链、关键失败与恢复、相邻区域交接和本阶段真实素材 |
| release | 明确准备可玩版本、交付运行包或修改全局基础 | 已实现范围的完整自动检查、构建与资源完整性、固定核心流程和发布范围的连续主线；支持平台的实际验证 |
| audit | 原版版本、解析器、媒体策略或历史资料核对 | 对应完整来源差分、媒体像素、重建或档案复核；由变化范围选择 |

task 是默认反馈方式。“任务完成”与“发布一个完整游戏版本”分别使用 task 和 release。phase 覆盖本阶段承诺的内容；完整区域遍历由其范围决定。档位相同不代表每次都执行同一套全局文件。

历史截图、旧日期报告和交接档生成器的可重放性归 audit，不作为每次任务的前置。仍承诺支持的旧存档格式必须提炼为持续执行的兼容性案例，不能一起移入历史检查。

### 改动与测试范围的映射

| 改动 | 规则或组件范围 | 内容与来源范围 | 浏览器范围 |
| --- | --- | --- | --- |
| 只改说明文档 | 文档引用检查即可 | 无运行内容变化时不执行 | 无 |
| 对白或地图布置 | 涉及的新规则；否则复用既有保障 | 变化的包、字体、入口和依赖 | 相应地图或对白 |
| 新区域复用既有机制 | 新事件链及关键恢复，原有机制无需复制测试 | 新登记入口全部准入；新原文件与输出核对 | 本阶段剧情与相邻交接 |
| 战斗公式或调度 | 战斗规则整组及相关状态、结算边界 | 使用受改机制的角色和技能绑定 | 代表战斗；涉及表现时观察动作 |
| StoryFlow 或事务机制 | 剧情整组、跨图、保存、取消、战斗返回 | 反向依赖到的区域；关键旧链代表实例 | 一条涉及该机制的旧链和新链 |
| 时钟或场景生命周期 | 引擎适配、探索、战斗、剧情及暂停相关边界 | 需要的代表内容 | 核心探索至战斗再返回流程及暂停恢复 |
| 存档格式或世界公共结构 | 保存恢复、迁移、并发提交、各持有者组件 | 支持的旧格式固定样例 | 真正写盘、退出与重载 |
| DAT 或 DGP 等解析器 | 对应格式和畸形输入 | 该解析器处理的全部受影响来源；增量构建及独立差分 | 代表地图或动作 |
| 图集、加载或纹理策略 | 资源租约、取消、缓存和显示边界 | 受影响图集的引用、来源像素和完整性 | 冷热加载、首次动作及重复进入释放 |
| Phaser 版本或渲染器 | 引擎适配整组及关键组件 | 引擎和渲染资源 | 扩大到支持环境和核心流程 |

多个系统同时变化时取并集，测试去重执行。世界公共结构、全局旗标语义、共享控制流、时钟、来源版本或依赖分析自身变化，应主动扩大范围。

固定核心冒烟围绕启动与恢复、探索与交互、地图至战斗再返回、保存重载以及暂停恢复建立精简集合。按照任务涉及的风险选取；引擎等全局变化执行整套，文档和孤立数值变化无需机械打开浏览器。

## 测试选择与结果复用

### 清单应表达的最小信息

先扩展现有 `tests/suites.json`，保持一个清单和现有 Node、Python 运行器。逻辑测试组至少声明稳定 ID、层级、系统、内容范围、特殊输入、环境和适用档位；代码依赖优先从真实 import 关系推导。数据驱动和动态加载的依赖由内容清单或显式登记补足。

以下仅示意目标字段，不是现有清单格式，也不承诺该输入表已穷尽实际依赖：

```json
{
  "id": "battle.clock",
  "files": ["test_battle_clock.mjs"],
  "layer": "component",
  "domains": ["battle", "engine-clock"],
  "content": [],
  "modules": ["web/core/combat.mjs", "web/phaser/runtime.mjs"],
  "inputs": ["web/data/battle_scheduler.json"],
  "requires": ["node"],
  "profiles": ["task", "phase", "release"]
}
```

迁移初期按文件选择即可；混合职责的文件先拆清环境和范围，再逐步支持稳定案例 ID。不能只靠 `*battle*` 文件名猜测影响；例如复活需要同时关联道具、战斗状态和保存结果。

### 影响范围的计算

从实际改动文件及登记差异出发，合并代码反向依赖、内容引用和显式跨系统关系。未跟踪文件、删除、重命名和工作区改动都要计入；不能只看上次提交。

共享事件、资源、旗标读写或配置被修改时，沿反向依赖扩大到所有受影响使用者。条件的运行值不能用于删除仍然存在的依赖。无法可靠判断的改动升级为相关系统整组；公共基础或未知全局依赖升级为更宽检查，不能默认为零项。

先采用少量明确的系统映射和现有内容登记，逐步补足实际漏选路径。不要为了选择测试，先构建一个比游戏本身更复杂的分析框架。

执行前输出选择原因、环境缺项和预计耗时，使“为什么这次又检查了旧区域”可直接追溯。任务报告列出本次检查和复用范围；不以测试总数当作完成标准。

### 复用条件和失效范围

成功结果以测试组为单位绑定测试及辅助代码、生产代码的依赖闭包、语义数据、相关原文件及产物指纹、运行器和所需环境版本。测试或 oracle 改变也必须失效。Node、Python 依赖、Phaser、平台、浏览器和渲染器按测试实际使用情况进入身份。

文件存在或 mtime 相同不足以证明可以复用。相同源输入与转换版本可以复用媒体和来源校验；修改解析器则使其所有受影响输入重新验证。缓存索引自身与依赖登记改变时也要保守失效。

`chapter_story.json` 等大汇总文件的单一哈希不能永久成为所有区域的依赖。随着内容增长，应复用现有分地图故事包，按稳定内容 ID 和语义摘要选择依赖；共享部分变化继续反向扩散。读取这些包的机制本身要先得到规则和来源验证。

测试完成后只对本组依赖复核指纹。测试期间相关输入变化使该组失效；文档或独立无关内容变化不应让整轮测试作废。构建先收口，验收期间保持运行输入稳定，减少可避免的重跑。

真实浏览器观察独立保存代码、配置、媒体及环境身份。旧截图不能升级成新版本实玩证据；复用自动检查也不能替代尚未执行的新事件链。release 保留必要的重新执行与干净构建检查，避免选择或缓存错误长期隐藏。

### 统一调度和结束条件

构建、定向回归、资源检查、浏览器观察和汇总属于同一次验收计划。`verify_current.py` 与 `verify_tests.py` 最终应共享选择和结果存储，汇总已满足的检查，而不是各自重新启动一套 all。

顺序为实现收口、必要导出、自动检查、正式浏览器、最终汇总。浏览器发现故障后修复，只重跑受影响检查和对应场景；已通过且相关输入不变的部分不重复执行。

所选范围全部通过且输入稳定即可结束。缺前置、未执行和通过分别报告，不能用 skip 冒称完整验收，也不因请求的是 task 就隐含执行 release。性能预算不构成丢弃必要测试或把失败移出范围的理由。

## 案例与辅助代码设计

规则单测使用能触发行为的最小有效数据，避免每个条件判断重新编译全部角色、道具和区域。完整结构的校验放在专属合同案例；校验器单测覆盖非法身份、缺字段、越界和拒绝写入等失败类型。

公共 fixture 与 harness 放已提交的 `tests/helpers`。只读的大样本可以复用解析结果，单个案例拥有独立可变状态；不能通过共享草稿或跳过有效性检查换取速度。组件测试调用真实规则和控制器，只替换时钟、文件接口、加载器等外部边界，避免另写一套游戏执行器作为测试答案。

固定 RNG、时钟、初始世界和输入序列，以状态与业务事件判断结果：奖励只提交一次、库存守恒、取消不改变世界、暂停不推进逻辑、旧回调不越权。避免断言无业务意义的私有方法调用次数、对象池内部排序或完整巨型快照。

来源测试使用独立推导的固定字段、原字节片段或独立核对路径，避免用导出器自己的输出计算“期望输出”。原版路径由统一解析器按实际文件身份定位，避免在大小写敏感环境误报缺失。

故障修复首先定位最小可保护边界：规则错误用规则案例，绑定错误用内容案例，引擎事件错误用 Phaser 集成案例。简单文案和可逆布局调整无需为了形式增加单测；高风险故障则保留能稳定复现的回归案例。

浏览器中需要观察 Canvas 内部状态时，可以增加只读诊断接口，暴露阶段、事件进度、逻辑时钟及资源计数。正式流程测试通过真实输入和正式导入入口推进，不直接改旗标绕过条件；使用阶段交接存档时明确其前置，连续主线验收另行记录。

## 执行预算与持续增长

以下是优化后的工程目标，后续应在固定参考机器上测量验证，尚不是当前实测承诺；浏览器人工操作和必要的大资源生产单独记录。

| 范围 | 建议目标 | 超出时的处理 |
| --- | --- | --- |
| 受影响规则与组件反馈 | 通常 5 至 15 秒 | 检查全表编译、过大 fixture、真实等待和重复初始化 |
| 普通 task 自动检查 | 通常 15 至 60 秒 | 排查范围误扩、重复校验和慢项；扩大检查有明确原因 |
| phase 自动检查 | 通常数分钟 | 按独立内容包分片，保留阶段内必要完整覆盖 |
| release 与 audit | 按已实现规模和素材量单独预算 | 批处理、受控并行、结果复用与可恢复执行；不挤入每次普通任务 |

预算约束反馈方式，不能通过减少业务覆盖来伪装达标。新增地图主要扩大内容清单和阶段案例；新增通用机制才扩大共享行为测试。地图数量增长时，全游戏验收成本仍会增长，普通任务的反馈应尽量接近“变化内容加受影响依赖”的成本。

统计选择、指纹、初始化、执行、构建和浏览器各阶段的耗时，分别记录单次值与稳定环境下的分位数。慢项按实际责任优化；不能只增加超时或删断言。Node 和 Python 可以在只读且相互独立时受控并行，媒体与浏览器任务限制并发，避免内存争用导致误报。

失败需要区分产品行为、前置缺失、测试隔离、输入变化和不稳定时序。偶发失败要保留首个现场并修复等待或隔离机制，不能以自动重试到绿作为通过标准。

每个新案例需要能回答：它保护哪种机制或实际内容差异、应由什么改动触发、已有案例为何不能覆盖。测试数量、行覆盖率和历史报告数量都不直接作为交付指标。

## 现有测试的迁移顺序

1. **先调整任务验收口径与分类。** 建立 task、phase、release、audit 的含义，扩充现有清单的系统、内容和环境标签；实施时同步 AGENTS、工具说明和区域方法，消除普通任务必须 all 的冲突。保留旧入口兼容，不先做大规模目录搬迁。
2. **修正混合职责和明显慢项。** 将 `test_map_collision.mjs` 的原 DAT 核对与纯移动行为分开；将 `test_fire_valley_npc_interactions.mjs` 的完整多态遍历归扩大范围，普通任务执行受影响入口；精简配置测试的重复全表编译。迁移时保留既有有效断言和真实绑定案例。
3. **补齐 Phaser 的小型真实集成集合。** 复用正式场景、时钟、显示适配和输入连接，覆盖暂停恢复、重进、取消、共享资源与一条实际游戏冒烟；将已有假 Canvas 测试按其能证明的范围分类。增量补齐缺口，不另写整套重复场景。
4. **统一选择和结果复用。** 从显式系统映射和内容依赖开始，让汇总工具消费相同验收结果，再按真实漏选案例完善依赖。保留独立的扩大验证，用来发现遗漏的依赖和缓存问题。
5. **逐项处理重复与过时保障。** 对名称相近的测试确认各自能发现什么故障。纯重复断言合并，旧实现细节断言改为当前业务合同，历史复现移到 audit，支持中的兼容案例继续保留。每次迁移选择能证明保障仍然存在的检查，不在每步改目录后重跑全部来源和媒体。

实施完成的判据是：普通任务能够解释选择范围；代码环境运行不再依赖未声明原版材料；新增同机制内容复用案例运行器；正式 Phaser 冒烟覆盖关键边界；相同输入的结果可可靠复用；全局变化会保守扩大检查；达到本次验收范围后自动结束。

例如后续接入另一个复用既有机制的城区，主要增加其入口和依赖数据、阶段案例及正式浏览器流程；只有发现新指令、服务规则或表现机制时，才扩充相应共享测试。旧地区保留增量内容校验、受影响的边界案例和扩大验收能力，避免逐城区叠加一份相同的全套战斗、保存和取消测试。
